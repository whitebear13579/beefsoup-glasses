# 使用者版本增量規格 v0.4（2026-10-15）

本文件承接 SPEC v0.2。使用者已確認連續翻譯與自動播報，以及在本機電腦新增視覺模型並保留人工確認／修正。以下是本輪實作與驗收的範圍；硬體驗收結果另記，不能由設計推定通過。

## 1. 使用流程

- **會議**：連接眼鏡 → 選擇音訊或包含重點影像 → 開始 → 讀逐字稿／摘要 → 停止並保存。
- **翻譯**：完成電腦連線設定 → 選目標語 → 開始連續翻譯 → 逐句看到原文、譯文與播報狀態；可靜音／重播／停止。
- **重點**：只呈現選中的照片與 OCR，顯示來源時間與判斷原因；可確認、修改文字、排除。
- **設定**：推論連線、目標語與權杖；診斷與模擬來源收進進階設定。權杖不寫入會議事件或一般偏好設定。

首頁不顯示沙盒路徑、WebSocket 協定、PCM 佇列等工程細節；待處理內容以「尚有片段待轉譯」呈現。錄製中停止按鈕必須容易找到。

## 2. 重點影像 pipeline

```text
H.264 → 全部參考影格解碼 → 約 1 fps 低成本 OCR／畫面品質
     → 文字穩定或畫面穩定的全畫面候選（非固定中央 ROI）
     → 同時最多一個視覺請求／限制頻率
     → 本機視覺模型 + 近期逐字稿
     → 分類與保留決策 + 動態 ROI
     → 實際裁切 ROI → 第二次辨識可見文字
     → 選中的原始影格照片 + OCR + 判斷來源
     → 使用者確認／修正 → 可引用的會議重點
```

### 2.1 選取原則

- 候選可由兩條路徑形成：全畫面 OCR 至少 4 個正規化字元且相鄰文字穩定，或 16×16 亮度縮圖顯示場景穩定且有足夠對比。第二條不要求手機先正確辨識多語文字；語意重要性仍由視覺模型判斷。尚未加入獨立模糊分數、字體尺寸評分或眼動追蹤。
- 視覺模型接收整張候選，辨別白板、投影片、文件、手機／電腦螢幕、產品標籤或其他場景；不是單靠 OCR 關鍵字決定。
- 白板／投影片／文件須與會議內容相符。個人手機與產品標籤預設排除；即使產品是討論主題，第一版也由使用者明確保留。
- 模型先找重點所在的 ROI；後端實際裁掉外圍，再以裁切影像進行第二次 OCR，第二次請求不帶全圖 OCR 或討論脈絡，降低補字與背景污染。保留全圖供使用者對照。模型內部使用 0–1000 整數座標，API 一律轉成 0–1 正規化座標。
- 不確定、模糊、空白或模型回應格式不合法時，不自動形成正式重點。不得以語境「補齊」看不清的數字或名字。
- 重複畫面與相近文字應合併；有內容更新才新增。不是每秒保存一次畫面。

### 2.2 資料與保存

每筆重點包含 ID、session／epoch、媒體 PTS、JPEG 相對路徑、原始手機 OCR、視覺模型 OCR、場景類型、ROI、判斷原因、模型名稱、確認狀態與使用者更正。

候選影像僅短暫保留於記憶體；拒絕候選不保存成會議照片。視覺請求逾時時仍持續錄音，不累積未受控的影像磁碟佇列。正式影像先原子寫檔後寫事件；事件不引用半寫入的照片。圖片置於 App 私有會議目錄，刪除會議時一併刪除。

第一版模型選中的片段以「待確認」顯示；使用者確認後才送作摘要 OCR 證據。舊版本每秒產出的 OCR 只能視為歷史原始觀測，不能自動升格為重點。

記錄 `vision_candidate`、`vision_review`、`vision_error` 診斷事件，區分沒有候選、模型拒絕、服務失敗及選中；只記 PTS、決策／類型或受限錯誤原因，不保存拒絕影像與其 OCR。診斷寫入不得中斷視訊處理。人工保留使用手機 OCR，必須標示來源；不冒稱已由視覺模型修正。

### 2.3 模型與算力

既有 jaahas/qwen3.5-uncensored:4b 的本機 capabilities 沒有 vision。新增 **`qwen3-vl:2b-instruct`** 本機基線，與文字模型分開設定。必須使用明確的 instruct tag；本機實測 `qwen3-vl:2b` 預設 thinking 版本在有限 token 下可能沒有輸出 JSON。視覺 API 與音訊 WebSocket 分開，避免視覺請求佔住音訊訊息處理；共享 GPU 的實際競爭仍需量測，必要時降低影像頻率。

參考：[Ollama Qwen3-VL 2B Instruct](https://ollama.com/library/qwen3-vl:2b-instruct)、[Vision API](https://docs.ollama.com/capabilities/vision)、[Structured outputs](https://docs.ollama.com/capabilities/structured-outputs)。模型的分類／重要性分數不是經校準的正確率。

### 2.4 第一版資源上限

| 項目 | 實作值／失敗行為 |
|---|---|
| 抽幀 | 約 1 fps 執行 OCR；H.264 參考影格仍正常解碼 |
| 文字穩定 | 正規化字元 bigram Jaccard ≥ 0.65；相同內容 ≥ 0.9 不再送 |
| 畫面穩定備援 | 16×16 Y 亮度縮圖，對比範圍 ≥ 30；扣除整體亮度差後，平均絕對差 ≤ 12。這些是可調門檻，不是經校準的清晰度或正確率 |
| 推論頻率 | 至少間隔 8 秒；手機同時最多一筆請求，忙碌時略過新候選 |
| JPEG | 手機品質 85；伺服器接受 ≤ 512,000 bytes、每邊 32–2048、總像素 ≤ 2,000,000 |
| HTTP | request body ≤ 750,000 bytes，影像 Base64 ≤ 700,000 字元；回應 ≤ 32 KiB |
| 逾時 | 模型兩次請求共用約 45 秒預算；手機 call timeout 55 秒；失敗不停止錄音 |
| 佇列 | 不累積照片待送磁碟佇列；伺服器一次一筆視覺推論，忙碌回 429 |

相鄰比較不保證跨場景全域去重。請求失敗或手機忙碌時解除該候選的去重標記，保留至少 8 秒節流，讓未改變的畫面稍後可重試；不建立待送影像佇列。未設定 PC 時不做自動候選 JPEG 請求。使用者可手動保留下一張可解碼影格，並核對／修改其手機 OCR。

## 3. 連續 STT → 翻譯 → TTS

```text
AAC → 本機保存 + 16 kHz PCM → STT → 重疊去除／句子累積
    → 已定稿句子 → 文字模型翻譯 → 原文與譯文事件
    → 有界播報佇列 → Android TTS → 實際音訊路由
```

- STT 和翻譯保持明確分工；不將原始音訊交給純文字模型。
- 音訊切片不等於句子。未完整的來源先顯示辨識內容，句末或最大等待邊界才形成可播報譯句；切片重送不重複播報。
- 原文、譯文、播報事件各有 session、epoch、句子 ID。換會議、停止、斷線重連與重複 ACK 不得播出上一會議內容。
- 目標語使用明確選項；TTS 啟動時檢查引擎及語音資料，缺少語音只停播報，逐字稿和錄音繼續。
- 播報佇列有上限；落後時清楚提示，不讓使用者一直聽到很久以前的內容。靜音立即取消排隊內容，解除靜音只播新的譯句。
- 會議紀錄模式預設不播報，連續翻譯模式依使用者選擇自動播報。歷史補送不自動念出；可手動重播。
- 原始收音不因播報而關閉。SDK 眼鏡音訊不能直接套用手機 AudioRecord 的 AEC。眼鏡開放式喇叭的聲音可能被麥克風錄回，必須以實機測試實際路由、回音及他人同時說話；未通過前不得宣稱可無回音全雙工翻譯。
- 連續翻譯時，若 Whisper 判定來源語言與目標語言的基礎語言相同且信心 ≥ 0.8，保留錄音及原文，但不再形成譯句／自動播報，回傳 `speechSuppressed=already_target_language`。此規則降低已觀察到的譯音循環，也會略過真正參與者所說的目標語播報；不能區分聲源、不能消除錄音中的回音，混語或低信心片段仍可能漏過。

使用 Android 系統 TextToSpeech 和 UtteranceProgressListener，不使用與 SDK 串流互斥的 ViveGlass speakText。參考：[TextToSpeech](https://developer.android.com/reference/android/speech/tts/TextToSpeech)。

### 3.1 當前 pipeline 的並行邊界

手機錄音保存／PCM、影像解碼／OCR、視覺 HTTP、語音 WebSocket、Compose 與 TTS 各自獨立。PCM 使用既有 4 秒窗口、0.5 秒重疊及最多 4 段在途；先持久化，結果核對後才移除待送檔。PC 同一 WebSocket 的 STT→句子定稿→翻譯目前仍依序執行；本版沒有宣稱 STT 與文字模型已在同一會議完全平行，或做到逐 token 語音串流。

句子暫存超過 12 秒媒體時間或 1000 字元也會定稿；停止時沖洗最後未完句。重疊去除是限制在重疊音訊時間範圍內的文字比對，不是 word timestamp 對齊，仍須用重複說話及多語語料檢查誤刪。播報最多保留 3 個待播句；滿載時保留畫面文字並提示延遲，不無限排隊。

本次眼鏡實測已出現四秒片段把 `tomorrow` 認成 `model`；相同錄音保留 11.5 秒上下文時辨識正確。滾動上下文、穩定前綴與 word timestamp 對齊尚未實作，不能將句子累積等同已解決 STT 切片品質。應以同一批保存音訊回放比較，再選擇窗口／模型與延遲折衷。

### 3.2 API 增量

- `hello` 新增 `targetLanguage`（`zh-TW`／`en`／`ja`）與 `continuousTranslation`。同一 session／epoch 重連不能悄悄換設定。
- 連續模式的 `result.utterances[]` 及停止時的 `utterance` 含句子 ID、原文、譯文、語言、`startUs`、`endUs`。手機先保存 `translation_utterance` 再去重；補送歷史不自動播報。
- `POST /vision/review` 使用 HTTP Bearer token，request 含 `sessionId`、`epoch`、`ptsUs`、`ocrText`、`context`、`jpegBase64`；回應含同一身分、`keep`、`category`、`roi`、`text`、`reason`、`uncertain`、`model`。錯 token 401、輸入錯誤 422、超大 body 413、忙碌 429、模型不可用 503／格式錯誤 502。
- `ocr_remove` 移除 `v:<sequence>` 證據；修改先移除再送更正，排除不能留在下一次摘要中。既有顯示的摘要會清空，使用者可更新摘要。模型已經生成的舊摘要檔與歷史事件不作為新證據。
- Debug 可用 ADB reverse 的 loopback WS 做端到端開發測試；正式區網仍要求可信的 WSS／HTTPS，不能停用憑證驗證。

## 4. UI／UX

延續原生 Material 3，提供會議、翻譯、重點、設定四個主要目的地。保留深淺主題、系統字級、48 dp 觸控區、TalkBack 語意與系統返回。狀態必須區分：眼鏡未連線／連線中／已連線、正在啟動／錄製／收尾／已保存、推論離線、語音準備／播放／靜音／缺少語音。

重點頁是「照片＋辨識文字＋時間＋確認動作」，不是長串不帶來源的 OCR 字串。沒有結果時解釋原因，不顯示示範照片冒充真實會議。

## 5. 必須有意義的測試

| 層級 | 情境 | 斷言 |
|---|---|---|
| 單元 | 候選穩定性、節流、時間戳倒退、相同畫面 | 不連續送同一畫面；沒有固定 ROI 假設 |
| 視覺 API | 錯 token、超大或損壞 JPEG、錯 session、非法 ROI、模型拒絕／逾時 | 不形成正式重點，不阻塞音訊 |
| 視覺品質 | 白板＋瓶身、投影片＋手機、個人手機、低光、畫面到處有字 | 比對重點 precision／recall、ROI、OCR CER；不能只測單一大字白底 |
| 保存 | JPEG 原子提交、事件、重啟還原、修正、排除、刪除 | 原圖與文字可一一對照；排除內容不進摘要 |
| 句子狀態 | 跨切片句子、相鄰重疊、重送、句尾、停止沖洗 | 每句一次；原文／譯文／ID 對應 |
| 播報回授防護 | 連續模式同目標語／高信心、低信心及一般會議模式 | 只在約定條件抑制新譯句，原文仍保存；以實際回授錄音回放驗證，不冒稱 AEC |
| TTS | 未初始化、缺語音、重複句子、排隊上限、靜音、停止、換會議 | 不念舊結果，失敗不停止錄音 |
| 實際模型 | 已知語音→Whisper→文字模型→Android TTS 合成 | 非空且可解碼音訊；保留原文、譯文與時長，不以 Fake 替代 |
| Compose | 未連線、錄製中、設定、翻譯開關、重點確認／修改／排除 | 控制正確啟用、工程欄位不出現在首頁、照片和文字可操作 |
| 真機 | 眼鏡連續錄音並播報、鎖屏、暫停、來電、耗電／發熱 | 比對回授、收音缺口、p95 延遲及可懂度，需人耳確認 |

## 6. 實作順序與交付判準

1. 候選與重點資料模型、照片保存、視覺 API 與模型能力檢查。
2. 句子定稿、翻譯及 Android TTS，保留重送和失敗恢復。
3. 原生操作介面與重點照片對照、人工確認／修正。
4. API／單元／裝置測試與實際模型串接，最後做眼鏡實景及播報驗收。

每一項完成須列出實作、通過環境與剩餘限制。下載模型、建置 APK 或產生一筆 OCR，都不能單獨標記整個產品驗收完成。
